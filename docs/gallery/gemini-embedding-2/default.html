Gemini Embedding 2: one vector space for text, images, video, audio, and documents

Google's new embedding model turns any mix of video, audio, images, and text into a single 3,072-dimensional vector, so a sentence, a photo, and a podcast clip can be compared directly. It is built by converting a Gemini model into an embedder and training it contrastively. On most of the retrieval benchmarks it reports, it beats the commercial multimodal embedders it is compared against.

1. The problem: one index per modality

An embedding model maps an input to a vector so that related inputs end up close together. Search, retrieval-augmented generation (RAG), recommendation, deduplication, and clustering all rest on this one operation: find the nearest neighbours of a query vector.

Production systems have usually needed a separate model for each modality: a text embedder for documents, a CLIP-style model for images, another for video, and a speech-to-text step before audio can be searched at all. Each model has its own vector space, so a text query cannot be compared directly with a video clip unless some bridge connects them.

Gemini Embedding 2 replaces that set of models with a single model and a single space. Inputs can also be interleaved. One input might be an image together with a question about it, or a slide that mixes a chart and its caption, and the result is still one vector.

Gemini already understands every modality, so the embedder gets that understanding without separate image or audio encoders being bolted on. The authors call Gemini initialization the embedder's pre-training stage. Everything that follows is adaptation.

Not disclosed: parameter count, number of layers, hidden size, context length, and per-modality input limits. The only input detail given is for video evaluation: frames are sampled at 1 FPS, up to 32 frames.

3. Matryoshka embeddings: one vector, three sizes

The full embedding has 3,072 dimensions, which costs a lot to store for billions of items. With Matryoshka Representation Learning (MRL), the model is trained so that the first k dimensions are a usable embedding by themselves. Like nested dolls, the smaller embedding sits inside the larger one. Training adds one contrastive loss for each prefix length, and the paper optimizes specifically for 768, 1,536, and 3,072.

Each cell stands for 64 dimensions. To get a smaller embedding you truncate and re-normalize, with no retraining or second model. The paper does not report retrieval quality separately for each truncation size, so this widget shows storage only.

4. Training objective: contrastive learning (NCE)

The model is trained on (query, positive) pairs, sometimes with an added hard negative. For each query, the loss is a softmax over cosine similarities divided by a temperature τ, and it pushes probability toward the correct target. Every other target in the batch serves as a free negative (in-batch negatives).

The paper adds two details:

  • False-negative masking. When the same query or positive appears more than once in a batch, those copies are masked out instead of being treated as negatives. This matters most for classification tasks with few labels, where many items in a batch share the same "answer".
  • Instruction dropout. Training inputs usually carry a task instruction (for example, "retrieve a caption for this image"). That instruction is randomly dropped during training so the model still works when users send no instruction.

Toy demo: how the softmax over a batch behaves

The query is a text caption, "a dog catching a frisbee on a beach". The similarity values are made up for illustration and are not from the paper (the paper does not report τ).

A lower τ makes the softmax sharper, so the loss concentrates on the hardest negatives. Turn off masking and the second copy of the correct image is counted as a negative. The model is then penalized for ranking a correct answer highly, which is the problem masking fixes.

5. Training recipe: three stages

  1. Pre-fine-tuning (PFT). Large batches of noisy, web-scale query–target pairs, covering imagetextcode only. Each batch contains one task, and tasks are sampled at fixed rates. This stage aligns the model's representations to work as embeddings.
  2. Fine-tuning (FT). Cleaner, task-specific data that often includes (query, positive, hard negative) triplets, across textcodedocsimageaudiovideo. Batch sizes are tuned per task and mixture rates are set empirically. The authors say that balancing modalities here is sensitive to these choices.
  3. Model souping. The final model averages parameters from several checkpoints: from one run, from different runs, and with weighted averages. Section 8 shows that this lets a model gain on one domain without losing much on others.

Synthetic data. Gemini itself is used to generate and refine training data. The code ablation (Section 8) shows this is the single largest lever reported in the paper.

According to the paper's Figure 3, FT improves on PFT on most benchmarks. The gain is small for images, which PFT already covered, and largest for video, which PFT never saw.

Not disclosed: dataset sizes, exact mixture weights, step counts, batch sizes, and the temperature.

7. Audio: skip the transcript

The usual way to search speech is a cascade: run speech recognition (ASR), then embed the transcript. Gemini Embedding 2 can instead embed the audio directly. The paper compares both setups with the same model on the MSEB benchmark (MRR@10).

Fine-tuning on MSR-VTT and Vatex data improves those two benchmarks, but YouCook2, which was held out, drops slightly. Averaging the fine-tuned weights back into the base model keeps most of the in-domain gain and turns every benchmark positive. The 1:1 soup outperforms the 2:1 soup on all three. Souping gives a simple way to add a specialization without retraining from scratch.

9. Caveats and open questions

  • Closed model, thin recipe. The model is built on proprietary Gemini, and the paper omits model size, temperature, data sizes, and mixture weights. Outsiders cannot reproduce it.
  • Baselines. Several baseline numbers are self-reported or were collected through commercial APIs. Open multimodal embedders (for example, VLM-based ones) appear only in the specialized-domain table.
  • Not best everywhere. Voyage-3.5-mm still slightly leads on visual document retrieval (ViDoRe V2), the setting many enterprise RAG systems care about most.
  • Weak sub-tasks. Scores on instruction-following retrieval are very low (Core17 6.44, News21 2.64, Robust04 −0.44), and so are some reasoning-heavy tasks (SpartQA 8.74, TempReasonL1 7.77).
  • Small inconsistency. The baseline video scores in the souping ablation (MSR-VTT 68.2, YouCook2 55.9, Vatex 69.2) differ from Table 1 (68.0, 52.5, 68.8). This is probably a different checkpoint or evaluation setup, and the paper does not explain it.
  • No MRL quality curve. MRL is trained at 768, 1,536, and 3,072 dimensions, but the paper reports no results for the truncated sizes.
Bottom line. The paper shows that converting a strong multimodal LLM into an embedder (bidirectional attention, mean pooling, contrastive training in stages, synthetic data, and souping) produces one vector space that is competitive or best across text, code, images, video, audio, and documents. For practitioners, the useful results are that you can build a single index for all content types, and that you can index audio directly without a transcription step.

Future directions named by the authors: training with ranking signals from search systems, and end-to-end fine-tuning for agentic RAG.
