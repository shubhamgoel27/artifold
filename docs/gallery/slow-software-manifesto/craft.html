Own it. Shrink it. Slow it down.

Twelve rules for software that keeps your work in files you can open without it, carries only what it needs, and moves at the speed of the person using it.

I

Own it.

Your data should outlive the program that made it.

  1. 01

    Write it to a file.

    A text file from 1985 still opens today and will open in 2065. A row in someone else’s database opens until the company pivots. Save to a disk the user can see, name, copy and back up, and treat any cloud as a mirror of that file, never the original.

  2. 02

    Pick formats a stranger can read.

    Plain text, Markdown, CSV, JSON, SQLite. If the only way to read your data is the program that wrote it, you don’t own the data. You rent it, and the rent goes up.

  3. 03

    Let people take everything and go.

    Export is a feature, not an exit interview. One command, one folder, every byte, in the formats from point two. Software people can leave is software they choose to stay in.

  4. 04

    Work without a network.

    Offline is the normal state of the world: planes, tunnels, basements, outages. Opening your own notes shouldn’t require permission from a server in another time zone. Make the network an upgrade, not a precondition.

II

Shrink it.

Every line you don’t ship is a line that never breaks.

  1. 05

    Ship fewer features.

    Each feature is a promise you’ll keep forever: documented, tested, migrated, explained. Say no early and say it often. Spend the years you save making the remaining few sharp.

  2. 06

    Count your dependencies out loud.

    Every import is a stranger with commit access to your future. Know their names and what they’d cost to replace. If you can’t list them from memory, there are too many.

  3. 07

    Respect the machine you’re given.

    A ten-year-old laptop is a perfectly good computer that bloat taught to feel old. Measure startup time and memory like they’re bills, because for someone on cheap hardware, they are.

  4. 08

    Prefer boring tools.

    Technology that has been dull for twenty years already had its surprises. Spend your novelty budget on the problem, not the plumbing. Nobody ever lost a weekend to make being too stable.

III

Slow it down.

Speed is for the program. Patience is for the project.

  1. 09

    Let it wait.

    Not every keystroke needs to sync in 200 ms. Save on pause, batch on close, reconcile tomorrow. A program allowed to be a little late can be a lot simpler, and simple programs fail in ways you can read.

  2. 10

    Release when it’s ready, not when it’s Tuesday.

    A calendar makes a poor product manager. Fewer releases mean fewer migrations, fewer changelogs nobody reads, and a button that is still where it was last month.

  3. 11

    Start fast, quit clean.

    Open in under a second. Close without a dialog. Leave no daemon, no updater, no tray icon behind. A program that’s hard to leave isn’t loyal, it’s clingy.

  4. 12

    Leave it finished.

    Some software is done. Fix the bugs, keep it building, and let it rest. Finished isn’t abandoned. It’s a chair: nobody expects a monthly update to a chair.
