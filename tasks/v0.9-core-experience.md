# v0.9 — core experience, from five more weeks of use

Second audit of the live library. It has 133 projects and 140 files, and
it grows by about 38 projects per month. That rate is steady across June,
July, and August.

## The problems

1. **Artifold records an edit history and never shows it.** The provenance
   store holds 128 superseded entries. 16 live artifacts have prior
   revisions; the largest chains are 28 and 17 revisions long. The version
   dropdown reads filename versions only (`-v2`, `(1)`), which match 2 of
   133 projects. So the dropdown stays empty for every artifact the user
   actually iterates on.

   The chain is also time-blind. `carry_forward` copies the old entry
   whole, so every revision inherits the original `added_at`. The count is
   reliable. The times are not recorded.

2. **There is no usage signal.** Artifold records when a file appears. It
   never records when the user opens one. The only sort is creation time,
   so daily-driver trackers sink under one-off explainers.

3. **The thumbnail cache never deletes anything.** The cache key is
   sha1(path+mtime+size), so every edit writes a new thumbnail and keeps
   the old one. 513 files sit on disk, 133 are in use, and the 380 orphans
   hold 32.4 MB of the 44 MB total. The manifest keeps stale rows too:
   147 entries for 133 projects.

4. **Dead facet.** The tool filter holds two values, `claude` (118) and
   unlabeled (15). It takes permanent sidebar space and filters nothing.

## Not in scope

- A diff for in-place revisions. The store keeps hashes, not content, so
  the old bytes are gone. A revision list can show *that* the artifact
  changed and when. It cannot show what changed. A content store is a
  separate decision.
- `conceit` and `scale` in the dashboard. Both are parsed and unused, but
  the user deferred them.
- Category rebalance. Engineering holds 44% of the library again. Real,
  but it needs a design decision, not a patch.

## Review

Measured on the live 133-project library:

| | before | after |
|---|---|---|
| thumbnail cache | 513 files, 44 MB | 133 files, 12 MB |
| history marked for deletion | 128 of 128 | 29 of 128 (all dead artifacts) |
| provenance reads per scan | 670 parses of 546 KB | 670 lookups, 1 parse |
| scan wall time | 3.19 s | 2.28–2.41 s |
| artifacts showing history | 0 | 14 (longest chain 28) |
| sorts | 3 | 4 (+ "Most used") |
| tests | 48 | 86 |

### Two problems found while building

Neither was in the original plan, and the first was the more serious one.

1. **The history was on a 30-day timer.** A superseded entry's content hash
   is gone from disk by definition, so the plain orphan rule stamped every
   one of them: all 128 were counting down, 51 of them due within 14 days.
   The feature would have shipped onto a store that was deleting its own
   evidence. `gc` now exempts any revision reachable from a live head, and
   un-orphans the ones already marked. 99 entries recovered on the first
   scan.

2. **The store was re-parsed 670 times per scan.** No caching anywhere, at
   546 KB a read. Adding a chain walk per project would have made it worse,
   so the memo went in first. Net effect is a faster scan than before the
   feature.

### Honest limits

- Revisions cannot be diffed. The store keeps hashes, not bytes. The detail
  pane says so rather than offering a button that cannot work.
- Every existing revision reads "time not recorded", because the stamps are
  new. Listing 28 identical rows is noise, so that case collapses to the
  count alone. Times accrue from here.
- `open_count` starts at zero for the whole library, so "Most used" leans on
  revision count until real opens accumulate. Opens are weighted 3× a
  revision: opening is reading, revising is building.
- A `file://` dashboard cannot beacon. Opens are only counted under
  `artifold serve`.
